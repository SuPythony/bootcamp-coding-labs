Unique Pointer
--------------

Q1. List one or two benefits of using RAII to manage memory instead manually calling `new` and `delete`.
A1. Using RAII resources (allocated heap memory) are automatically deleted and managed when they go out of scope/program terminates. We never have to worry about managing memory. A consequence is that there are no worries of dangling pointers and double-frees.

Q2. When implementing move semantics for a `unique_ptr`, for example in the move constructor `unique_ptr(unique_ptr&& other)`, it is essential that we set the underlying pointer of the `other` parameter to `nullptr` before exiting the function. Explain in your own words what problem would arise if we did not.
A2. If we don't then there will be two pointers pointing to the same memory location. If we are not careful we might accidentally delete one of those pointers after deleting the other one which will result in a double-free and crash the program. Also this adheres to the name/function of unique pointers - only a single pointer existing at a time pointing to a particular memory location.

Q3. This method of recursive deallocation through RAII works great for small lists, but may pose a problem for longer lists. Why? Hint: what is the limit for how "deep" a recursive function's call stack can grow?
A3. Each delete on a particular node calls the delete of the next node. This only stops when we are at the end of the linked list (as the next pointer is nullptr). This can pose a problem as each new delete call (a function call) puts up on the stack and if the list is too big, a stack overflow might occur (as stack size is finite).

Q4. What does `std::move` do in this context? Why is it safe to use `std::move` and move semantics here?
A4. std::move creates an rvalue reference of the value passed. It is not 'safe' to use move semantics here per se as we could have similarly implemented these things in the copy constructor/assignment operators. We use move semantics as a convention that 'moves' the ownership, using the copy versions to, as the name suggests, just copy the data. As we are using pointers we prefer changing ownership to reduce the risks of dangling pointers and double-frees.

Q5. Why does `operator->` return `T*` (a pointer) rather than `T&` (a reference)? Walk through what the compiler does when it sees `ptr->member`.
A5. Because the -> operator expects a pointer as the left operand and dereferences that pointer to get the right operand. The compiler first calls any operator-> overload on ptr (or if not defined, ptr should already be a pointer). If it gets another object with overloaded operator->, repeat recursively. Then it dereferences the pointer returned and accesses the value corresponding to member in the object.

Q6. Why does this class need BOTH `T& operator*()` and `const T& operator*() const`? Give a one-line code example that would fail to compile if one of them were missing, and explain which one.
A6. The non-const version is needed for non-const declared instances and assigning values to the pointer's dereferenced object. The const version is needed to be able to dereference const objects. It doesn't allow modifying.
const unique_ptr<int> p{new int(1)};
int a = *p; // this will fail if const version is missing

unique_ptr<int> p{new int(2)};
*p = 3; // this will fail if non-const version is missing

Q7. We marked `operator bool()` as `explicit`. What kind of unintended code would compile if we had left the `explicit` off? Give a concrete example.
A7. Without explicit the compiler will implicitly convert an object of type unique_ptr to a bool wherever it needs to and is possible. But we don't want that and only want it to be converted in conditional expressions (if (ptr), while (ptr)), therefore we use explicit.
const unique_ptr<int> p{new int(1)};
int a = p + 1; // without explicit, this will work, p converts to true, which converts to 1 and a stores 2.
